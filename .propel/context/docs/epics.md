## Epic Description

### EP-TECH: Establish the localhost application foundation

**Source**: [SOURCE:RULE]

**Basis**: Green-field detected - infrastructure epic generated by rule.

**Business Value**: Provides a secure, testable localhost foundation so feature teams can deliver against stable frontend, backend, API, configuration, and runtime boundaries.

**Description**: Establish the separate React and FastAPI applications, clean dependency boundaries, generated API contract, validated runtime configuration, automated test stack, and loopback-only native development environment.

**UI Impact**: Yes

**Screen References**: SCR-001 through SCR-008

**Key Deliverables**:

- Separate frontend and backend applications with independent manifests and build outputs.
- Feature-sliced React shell and modular FastAPI composition root with inward-facing dependencies.
- Generated OpenAPI 3.1 contract and frontend contract-compatibility test.
- Typed startup configuration that rejects missing, contradictory, or unsafe settings.
- Unit, integration, contract, and end-to-end test foundations with core coverage enforcement.
- Separate loopback-bound development processes with exact-origin restrictions.

**Dependent EPICs**:

- None

### EP-DATA: Establish transient case state and lifecycle

**Source**: [SOURCE:RULE]

**Basis**: Data layer complexity detected - data epic generated by rule.

**Business Value**: Preserves evidence, revisions, approvals, and working files during an active case without creating prohibited durable records.

**Description**: Implement the in-memory case aggregate, immutable field and POC revisions, randomized temporary workspaces, protected configuration data, and idempotent lifecycle operations that clear all transient state.

**UI Impact**: No

**Screen References**: N/A

**Key Deliverables**:

- Backend-owned in-memory case aggregate and repository port.
- Immutable evidence, field revision, POC revision, and approval state model.
- Randomized per-session workspace with streamed file ownership.
- Idempotent memory and workspace cleanup with zero-residue verification.
- Startup behavior that exposes no recoverable case records.
- Protected environment-based configuration for credentials, secrets, and provider settings.

**Dependent EPICs**:

- EP-TECH - Foundational - Requires the backend module boundaries and validated runtime composition.

### EP-001: Intake documents and manage transient sessions

**Business Value**: Lets reviewers safely begin and end a CMS-2567 case while understanding upload limits, validation outcomes, and permanent transient-data removal.

**Description**: Deliver bounded document upload and CMS-2567 validation, clear rejection and replacement handling, active-session retention, inactivity cleanup, explicit end-session confirmation, and truthful cleanup outcomes.

**UI Impact**: Yes

**Screen References**: SCR-002, SCR-003, SCR-004, SCR-006, SCR-008

**Key Deliverables**:

- Streamed PDF and image upload with 50 MB and 200-page enforcement.
- CMS-2567 readability and structure validation before extraction.
- Rejection reasons, retry, replacement, and partial-file cleanup paths.
- Visible session-only retention and inactivity status across the workspace.
- Confirmed explicit session termination with memory and file cleanup.
- Cleanup failure state that retains the case and offers a safe retry.

**Dependent EPICs**:

- EP-DATA - Foundational - Requires transient aggregate and workspace lifecycle operations.

### EP-002: Extract evidence-linked deficiency data

**Business Value**: Reduces manual transcription and missed deficiencies by producing review-ready provider, F-tag, and complete SOD candidates linked to source evidence.

**Description**: Extract native text, invoke approved OCR for incomplete pages, request schema-constrained provider and deficiency candidates, validate evidence and uncertainty fields, and stream ordered progress to the reviewer.

**UI Impact**: Yes

**Screen References**: SCR-003, SCR-004

**Key Deliverables**:

- Page-level native text extraction with selective OCR fallback.
- Separate provider and deficiency candidates with complete SOD boundaries.
- Closed extraction schema requiring page, snippet, confidence, and uncertainty data.
- Application-owned OCR and LLM ports that keep provider SDKs outside the core.
- Ordered resumable SSE progress without document-text replay.
- Review-ready unconfirmed extraction results for every validated candidate.

**Dependent EPICs**:

- EP-DATA - Foundational - Requires transient storage for jobs, pages, evidence, and unconfirmed candidates.

**Business Value**: Keeps compliance judgment authoritative by enabling reviewers to resolve uncertainty, correct values, and confirm only evidence-supported deficiencies.

**Description**: Present provider and deficiency fields beside synchronized evidence, preserve original values through corrections, distinguish provenance, and block confirmation or drafting until all required values and evidence are resolved.

**UI Impact**: Yes

**Screen References**: SCR-004, SCR-005

**Key Deliverables**:

- Searchable deficiency review with synchronized page and snippet evidence.
- Candidate comparison and explicit supported-value or user-correction paths.
- Original and current values with immutable revision and provenance history.
- Confidence and uncertainty states that never imply false completion.
- Validation for F-tag, complete SOD, and supporting evidence.
- Confirmation gate that exposes drafting eligibility only for the current reviewed revision.

**Dependent EPICs**:

- EP-DATA - Foundational - Requires evidence spans and immutable field revisions.

### EP-004: Generate and edit grounded POC drafts

**Business Value**: Reduces correction-plan drafting effort while preventing unsupported facility-specific claims and preserving reviewer control over every section.

**Description**: Generate one five-part POC from each confirmed deficiency, validate every facility-specific claim against reviewed inputs, represent missing facts explicitly, and save reviewer edits as new unapproved revisions.

**UI Impact**: Yes

**Screen References**: SCR-006

**Key Deliverables**:

- Per-deficiency generation using only the selected reviewed context.
- Closed schema for affected residents, others at risk, corrective measures, monitoring, and completion date.
- Claim-to-evidence grounding validation and typed missing-information markers.
- Five stable section editors with section-level AI-generated and user-edited provenance.
- Immutable draft revisions and immediate approval revocation after edits.
- Readiness validation for complete current revisions.

**Dependent EPICs**:

- EP-DATA - Foundational - Requires confirmed deficiency and revision state ownership.

### EP-008: Recover processing with safe diagnostics

**Business Value**: Preserves valid reviewed work during failures and gives reviewers precise recovery actions without exposing PHI or provider internals.

**Description**: Standardize extraction, OCR, and POC-generation failures as correlated safe problem details, record affected stages without false results, support retry of only the failed operation, and verify sensitive content never enters logs.

**UI Impact**: Yes

**Screen References**: SCR-001 through SCR-008

**Key Deliverables**:

- Typed validation, authorization, provider, cancellation, and internal problem envelopes.
- Failed page or operation state that excludes unconfirmed payloads.
- Selective retry for failed extraction, OCR, or POC generation stages.
- Preservation of confirmed deficiencies and retained POC work across retry exhaustion.
- Correlation identifiers in API responses, job events, and structured diagnostics.
- Automated log-redaction checks for document, SOD, POC, credential, and provider payload content.
- Calm error presentation with retained-work statement, retryability, and one recovery action.

**Dependent EPICs**:

- EP-DATA - Foundational - Requires preserved job, review, and draft state for selective recovery.
